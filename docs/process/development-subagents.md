# 开发子智能体设计

制定日期：2026-06-07

本文档描述的是“完成本产品开发任务所需的开发子智能体”，不是产品内部面向用户的 AI Agent。当前产品本身仍然是本地工作区管理器，核心能力是工作区管理、软件扫描与启动、外部窗口切换、白板记录和本地保存。

## 1. 总体判断

这个项目不适合把子智能体拆得过细。拆得太细会导致大量交接成本，尤其是 Tauri 前后端、Windows 原生能力、SQLite 数据结构和白板状态之间有强耦合。更合理的方式是设置一个主控架构智能体，再配合少量专业子智能体，每个子智能体负责一个稳定边界，并交付可验证的代码、接口或测试。

建议第一阶段使用 7 个子智能体：产品与交互智能体、架构与任务拆解智能体、前端工作区智能体、白板 Canvas 智能体、平台适配智能体、数据与本地存储智能体、测试与验收智能体。许可证与开源复用可以作为架构智能体的固定检查项，不建议单独长期拆成一个智能体，除非后续依赖数量明显增加。

## 2. 主控架构智能体

主控架构智能体负责把 PRD、界面方向、技术栈和实际代码实现统一起来。它的核心任务不是写最多代码，而是定义模块边界、接口契约、数据流和验收顺序，防止不同子智能体各自实现一套概念。

它需要维护几个关键决策：前端只调用业务语义命令，不直接知道 Windows API；Rust 后端区分 domain、storage、platform、commands；平台能力通过 trait 或等价接口抽象；工作区、软件、窗口、白板节点的数据结构必须稳定，不能因为某个页面实现方便就随意改字段。

这个智能体的主要产出是开发路线图、模块接口、跨端数据类型、任务优先级和代码审查意见。每次进入新阶段前，它都要确认当前实现是否仍然符合 `docs/product/workspace-manager-prd.md`、`docs/product/ui-direction-notes.md` 和 `docs/specs/engineering-standards-and-tech-stack.md`。

## 3. 产品与交互智能体

产品与交互智能体负责把设计图纸转成可开发的页面结构和交互规则。它需要守住一个边界：界面中间区域可以是当前工作区概览、最近窗口截图或软件卡片预览，但不能被描述成真实外部软件内嵌容器。

它重点处理左侧工作区列表、中间当前工作区软件标签和软件卡片、顶部搜索与添加软件入口、右侧白板/操作记录之间的关系。它需要定义空状态、错误状态、加载状态、保存状态、窗口已关闭状态、软件已加入状态、重新打开状态这些真实产品状态。

它的主要产出是页面信息架构、交互说明、状态清单和 UI 验收标准。前端智能体实现页面之前，应该先拿到它定义的状态模型。

## 4. 前端工作区智能体

前端工作区智能体负责 React + TypeScript 侧的主界面实现，包括工作区列表、当前工作区标题、软件标签、添加软件弹窗、软件卡片、搜索框、设置入口和基础状态管理。

它不负责直接扫描系统软件，也不负责直接切换窗口。它只通过 Tauri command 调用后端，例如 `scanInstalledApps`、`launchApp`、`focusWorkspaceApp`、`listWorkspaceApps`、`saveWorkspace`。这样做是为了保证未来 macOS 迁移时，前端不需要知道平台差异。

它的主要产出是可运行的主界面、前端状态 store、API 调用封装、组件测试和 Playwright 主链路测试。验收重点是：用户能创建工作区，打开添加软件面板，搜索软件，添加后看到当前工作区软件卡片，点击卡片触发窗口切换命令。

## 5. 白板 Canvas 智能体

白板 Canvas 智能体负责右侧白板和操作记录。第一版应优先实现类似 Obsidian Canvas 的卡片式记录，而不是复杂绘图软件。技术上以 React Flow / xyflow 为主，Markdown 编辑使用 CodeMirror 6 或第一阶段先用 textarea 过渡。

它需要支持 Markdown 卡片、文本/便签卡片、图片或截图卡片、待办卡片、拖拽移动、缩放、选择、删除、撤销重做和自动保存。操作记录时间线可以先由用户手动添加，不做自动监听外部软件内部行为。

它的主要产出是白板组件、节点数据结构、节点持久化转换函数、操作记录组件和白板相关测试。它需要和数据存储智能体约定清楚持久化格式，避免 React Flow 的渲染字段直接污染数据库模型。

## 6. 平台适配智能体

平台适配智能体负责 Windows 第一版的原生能力，并为 macOS 迁移保留接口。它是本项目风险最高的子智能体，因为软件扫描、启动、窗口枚举、窗口恢复、窗口置前和图标读取都依赖系统 API。

Windows 侧需要实现扫描开始菜单快捷方式、读取注册表应用信息、支持手动 exe/快捷方式/URL/命令、启动软件、枚举窗口、根据进程和窗口句柄绑定工作区软件、恢复最小化窗口、尝试置前窗口。实现时必须处理失败原因，例如路径不存在、权限不足、窗口已关闭、系统拒绝焦点切换。

它的主要产出是 `src-tauri/src/platform` 下的平台接口和 `windows` 实现。前端和业务层不应该出现 `HWND`、`SetForegroundWindow`、注册表路径等平台细节。未来 macOS 智能体只需要实现同一组平台接口，内部再接 NSWorkspace、CGWindowListCopyWindowInfo 和 Accessibility API。

## 7. 数据与本地存储智能体

数据与本地存储智能体负责 SQLite 数据模型、迁移、Repository/Service 层和数据一致性。它需要把工作区、软件库、工作区软件关联、窗口绑定、白板节点、图片资源、操作记录和最近使用记录分清楚。

它要特别注意一个问题：系统软件和工作区内的软件条目不是同一个概念。系统软件表示“这台电脑上可启动的应用”；工作区软件表示“某个工作区里绑定了这个应用，并且可能有别名、备注、用途、窗口绑定和排序”。同一个 Chrome 可以在不同工作区里有不同用途。

它的主要产出是数据库 schema、迁移文件、Rust domain model、序列化 DTO、数据访问测试和备份/恢复基础策略。它还需要为白板图片资源定义存储方式，例如本地 app data 目录下的资源文件加数据库引用。

## 8. 测试与验收智能体

测试与验收智能体负责把 PRD 中的验收标准变成可执行测试。它需要分清三类测试：前端 Web UI 可以用 Playwright 自动测；纯业务和数据库逻辑可以用 Rust/Vitest 自动测；真实 Windows 软件扫描、启动和窗口切换需要真实系统环境下的集成测试或人工验收脚本。

它的重点不是追求测试数量，而是覆盖主链路和高风险边界。主链路包括新建工作区、添加软件、软件出现在当前工作区、点击软件触发窗口切换、创建 Markdown 卡片、粘贴图片卡片、关闭重开后数据仍存在。高风险边界包括窗口已关闭、启动失败、软件扫描为空、重复添加同一软件、不同工作区数据隔离。

它的主要产出是测试计划、Playwright 用例、Vitest 用例、Rust 单元/集成测试和 Windows 手工验收清单。每次重要功能合并前，它都应该给出明确的“已自动验证”和“仍需人工验证”的区别。

## 9. 推荐协作顺序

第一步由主控架构智能体和产品与交互智能体把 MVP 的页面状态、接口契约和数据模型定下来。这个阶段不要急着做完整 UI，先确定工作区、软件、窗口、白板这几个核心对象的字段和关系。

第二步让数据与本地存储智能体、平台适配智能体并行推进。数据侧先完成 schema 和基础 CRUD；平台侧先完成最小可用的扫描、启动、枚举、聚焦接口。两边都通过 Rust service 暴露给 Tauri command。

第三步让前端工作区智能体接入真实或 mock 的 Tauri command，完成主界面和添加软件链路。这个阶段就可以开始用 Playwright 测新建工作区、打开添加软件面板、添加软件卡片等前端主流程。

第四步接入白板 Canvas 智能体。白板不要一开始做得太重，先完成 Markdown 卡片、图片卡片、拖拽、自动保存和恢复。等主链路稳定后，再补操作记录时间线、截图预览和更多工具栏能力。

第五步由测试与验收智能体做端到端验收，把 Windows 真实窗口切换能力单独列出。只要涉及真实软件启动、系统窗口置前、管理员权限窗口、macOS 权限预留，就不能只看前端测试结果。

## 10. 不建议设置的子智能体

不建议单独设置“AI 功能智能体”。当前产品不是 AI 工作流产品，也不需要模型推理才能成立。过早加入 AI 总结、自动记录、自动识别用户操作，会引入隐私、权限和准确性问题，偏离 MVP。

不建议单独设置“插件市场智能体”。第一版只需要支持用户手动添加 exe、快捷方式、文件夹、URL 或命令，不需要做插件生态。

不建议单独设置“跨平台 macOS 实现智能体”作为第一阶段主力。第一阶段需要的是平台接口预留和 Windows 实现质量。macOS 可以在接口稳定后再进入实现阶段，否则会让 Windows MVP 变慢。

## 11. 最小可用团队配置

如果只能使用少量子智能体，最小配置是 4 个：主控架构智能体、前端工作区智能体、平台适配智能体、白板与数据智能体。测试职责由每个智能体自行承担，再由主控架构智能体做最终验收。

如果希望开发过程更稳，推荐使用 7 个：主控架构、产品交互、前端工作区、白板 Canvas、平台适配、数据存储、测试验收。这个配置既能覆盖项目主要风险，又不会把沟通成本推得太高。
