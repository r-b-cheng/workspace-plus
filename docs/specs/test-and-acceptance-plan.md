# 测试与验收计划

制定日期：2026-06-07

本文档面向第一版 Windows MVP，目标是把工作区管理器的核心链路转成可执行、可复验的测试与验收标准。测试范围覆盖新建工作区、添加软件、窗口切换、白板 Markdown/图片卡片、自动保存、数据隔离和失败状态。本文只定义测试与验收计划，不替代产品需求、技术选型或具体实现设计。

需要先明确边界：前端 Web UI、业务纯函数和数据库逻辑可以自动化验证；真实 Windows 软件扫描、启动、窗口恢复、窗口置前、权限受限窗口等能力必须在真实系统中验收。不能用前端 mock 测试结果替代系统级验收，也不能把依赖真实 Windows API 的用例伪装成普通单元测试。

## 1. 测试分层

Vitest 负责前端组件、状态管理和纯函数测试。它主要验证 React + TypeScript 侧的确定性逻辑，例如工作区列表渲染、添加软件面板筛选、已添加状态、白板节点增删改、Markdown 卡片编辑状态、图片卡片元数据、保存状态提示、错误提示文案和 Tauri command 调用参数。Vitest 不验证真实软件是否被打开，也不验证真实窗口是否置前。

Playwright 负责 Web UI 端到端流程测试。它应在前端开发服务或 Tauri 前端壳可测试环境中跑主链路，重点验证用户能从界面完成新建工作区、打开添加软件面板、搜索软件、添加软件后看到当前工作区软件卡片、创建 Markdown 卡片、添加图片卡片、切换工作区后数据不串、关闭重开前端后恢复状态。Playwright 可以 mock Tauri command 返回值来稳定覆盖 UI 主链路，但标记为 mock 的用例不能作为 Windows 原生能力通过的证据。

Rust 单元测试负责后端业务模型、错误类型、DTO 序列化、数据校验和平台接口以外的确定性逻辑。Rust 集成测试负责 SQLite schema、migration、Repository/Service、工作区删除语义、软件关联隔离、白板持久化、图片资源引用、窗口绑定记录和失败状态落库。依赖真实开始菜单、注册表、进程启动、窗口枚举、窗口激活的测试要单独归类为 Windows 集成或人工验收，不进入默认 `cargo test` 的快速测试集。

Windows 真实系统人工验收负责验证平台适配层是否在真实桌面环境中工作。验收对象包括开始菜单和注册表扫描、手动添加 exe/快捷方式/URL/命令、启动真实软件、识别进程和窗口、最小化窗口恢复、被遮挡窗口置前、窗口关闭后的重新打开提示、权限不足或路径失效时的明确错误。人工验收必须记录系统版本、应用版本、被测软件、权限状态和失败截图或日志。

## 2. Vitest 用例范围

工作区相关测试应覆盖没有工作区时的空状态、新建工作区表单校验、创建成功后进入新工作区、重命名后列表和标题同步、删除确认文案中明确说明不会卸载软件或关闭真实窗口。工作区切换时，当前工作区的软件卡片、白板节点和操作记录必须从当前工作区数据源读取，不能残留上一个工作区的 UI 状态。

添加软件相关测试应覆盖软件搜索过滤、分类展示、已加入当前工作区状态、重复添加时转为切换窗口行为、添加失败时显示具体原因。前端传给 Tauri command 的参数必须是业务语义，例如 `launchApp`、`focusWorkspaceApp`、`listWorkspaceApps`，不能出现 `HWND`、注册表路径、`SetForegroundWindow` 等平台细节。

白板相关测试应覆盖 Markdown 卡片创建、编辑、预览、删除、拖拽位置更新、缩放状态不污染持久化模型、图片卡片通过文件引用或资源 ID 保存、撤销重做对节点列表的影响、自动保存状态从“保存中”变为“已保存”或“保存失败”。React Flow 渲染字段应在转换函数中剥离，持久化对象只保存跨平台可读的数据。

失败状态测试应覆盖软件扫描为空、启动失败、窗口已关闭、保存失败、图片资源缺失、数据库返回冲突、网络 URL 或命令无效等状态。每个失败状态都需要有可见反馈和下一步操作，例如重试、重新打开、移除关联或手动选择路径。

## 3. Playwright 用例范围

第一条主链路是工作区创建与恢复：打开应用后，如果没有工作区，用户能看到新建入口；输入名称创建工作区后，左侧工作区列表出现新项，主区域标题切换到该工作区；刷新或重新打开前端后，应用进入最近使用的工作区，并显示保存状态。

第二条主链路是添加软件：用户点击“添加软件”，面板展示已扫描或 mock 的软件列表；输入关键字后结果即时过滤；点击某个软件后，面板关闭或状态变化，当前工作区的软件标签或软件卡片出现该软件；再次搜索同一软件时显示“已在当前工作区”，点击后触发切换窗口命令而不是重复添加。

第三条主链路是白板记录：用户创建 Markdown 卡片，输入标题和正文，切换预览后 Markdown 渲染正常；用户添加图片卡片，图片在画布或右侧白板区域可见；拖动卡片后位置发生变化；等待自动保存完成后刷新页面，Markdown 内容、图片卡片和位置恢复。

第四条主链路是数据隔离：用户在工作区 A 添加软件和白板卡片，再切换到工作区 B；工作区 B 不显示工作区 A 的软件卡片、Markdown 内容或图片卡片；在工作区 B 添加不同内容后切回 A，A 的数据仍保持原样。这个用例是 MVP 必测项，因为产品价值建立在工作区上下文隔离上。

第五条主链路是失败反馈：mock `launchApp` 返回路径不存在、权限不足或启动命令无效时，界面必须展示明确错误原因；mock `focusWorkspaceApp` 返回窗口已关闭时，界面必须展示“窗口已关闭”一类提示，并提供重新打开入口；mock `saveCanvas` 失败时，顶部保存状态必须变为失败或待重试，不能继续显示“已保存”。

第六条主链路是快速切换：用户通过配置的快捷键打开快速切换面板，输入当前工作区内的软件名称、别名或用途备注，键盘选择结果并按 Enter。已运行窗口应调用聚焦命令；窗口已关闭时应显示重新打开入口；未加入当前工作区但来自系统软件库的结果应显示“添加并打开”。Playwright 可以通过测试钩子模拟快捷键打开面板，但不能证明系统级全局快捷键注册成功。hook 不是系统热键证据；注册、冲突、真按键和真切窗的人工清单在 `docs/dev-plan/packages/pkg-09-p0-acceptance/windows-hotkey-manual-acceptance.md`，自动 / 人工对照见同目录 `verification-matrix.md`。

## 4. Rust 单元与集成测试范围

Rust 单元测试应覆盖领域模型和服务层规则。工作区实体需要验证名称校验、最近使用时间更新、删除语义和序列化字段；系统软件与工作区软件必须是不同模型，同一个系统软件可以在不同工作区有不同别名、备注、排序和窗口绑定；白板节点需要验证 Markdown、文本、图片、待办等类型的合法字段。

SQLite 集成测试应使用临时数据库，覆盖 migration 可重复执行、工作区 CRUD、软件库写入与去重、工作区软件关联、窗口绑定记录、白板节点保存和恢复、图片资源引用、操作记录保存、删除工作区后的级联清理。删除工作区只能删除本地数据中的工作区关联和白板内容，不能调用平台层关闭窗口、卸载软件或删除系统程序。

平台接口的非系统实现可以用 fake adapter 测试业务调用顺序。例如 `launchWorkspaceApp` 在启动成功后应写入工作区软件关联和窗口绑定；重复添加同一工作区软件时应调用窗口聚焦路径；窗口不存在时应返回 typed error，并保留工作区软件关联以便用户重新打开。这里验证的是业务层处理，不验证真实 Windows API。

Windows 原生集成测试如果进入自动化，应放在独立测试目标或带显式开关的测试集中，例如需要 `WINDOWS_NATIVE_TESTS=1` 才运行。它可以覆盖扫描、启动和枚举的最小真实路径，但不能作为默认 CI 快速测试，因为它依赖机器环境、已安装软件、权限和桌面会话状态。

## 5. Windows 真实系统人工验收

人工验收环境应至少记录 Windows 版本、应用构建版本、数据库初始状态、被测软件列表和是否以管理员身份运行。建议使用系统自带或常见软件组合，例如 Notepad、Windows Terminal、File Explorer、Chrome 或 Edge、VS Code。不同机器扫描结果不一致是正常现象，验收重点是产品能显示可理解结果，并允许用户手动补充路径。

新建工作区验收：首次打开应用时创建“验收工作区 A”，确认工作区列表出现该项，当前工作区标题同步，保存状态正常。再创建“验收工作区 B”，确认可以在两个工作区之间切换，并且最近使用记录在重启应用后生效。

添加软件验收：在“验收工作区 A”中打开添加软件面板，搜索 Notepad 或其他确定存在的软件，点击添加后真实软件被启动，当前工作区的软件区域出现对应条目。重复添加同一软件时不应出现重复条目，应进入窗口切换或已加入状态。手动添加一个有效 exe、一个无效路径和一个 URL，分别确认成功、明确失败和正确处理。

窗口切换验收：把已添加软件窗口最小化后，点击产品中的软件条目，窗口应恢复并尝试置前。把窗口放到其他窗口后面，再点击软件条目，窗口应切到前台。手动关闭该软件窗口后，再点击软件条目，产品应提示窗口已关闭，并提供重新打开入口。若系统拒绝置前或权限不足，产品应显示明确失败原因，而不是无反馈。

快速切换验收：在设置中确认快捷键为 `Ctrl+O` 或用户自定义组合；按下快捷键后快速切换面板应出现在当前应用中；输入软件名或别名后结果即时过滤；按 Enter 后能切换到对应外部窗口。若 `Ctrl+O` 与当前前台软件冲突或系统拒绝注册，产品应提示快捷键不可用，并允许用户改用其他组合。

白板验收：在“验收工作区 A”创建 Markdown 卡片，输入标题、列表和链接，确认编辑与预览可用；粘贴剪贴板图片或拖入图片文件，确认图片卡片出现；拖动卡片并缩放画布，等待自动保存状态变为已保存。关闭并重新打开应用后，确认 Markdown 内容、图片卡片和位置恢复。

数据隔离验收：在“验收工作区 B”中确认不显示 A 的软件条目和白板卡片；在 B 中添加另一个软件和一张 Markdown 卡片，切回 A 后确认 A 的内容未被污染。删除 B 时，确认提示文案说明只删除工作区数据，不卸载软件、不关闭真实窗口；删除后系统中的真实软件仍可正常打开。

失败状态验收：移走或重命名一个手动添加的 exe 后尝试启动，产品应提示路径不存在；用权限受限目标或无效命令启动时，产品应提示权限不足或命令无效；模拟或制造保存失败时，顶部保存状态不能显示已保存。所有失败都应能被用户理解，并提供重试、重新选择路径、移除关联或重新打开等恢复动作。

## 6. 验收通过标准

MVP 通过验收的最低标准是：自动化测试覆盖前端主链路、业务规则和持久化规则；Windows 人工验收覆盖真实软件启动和窗口切换；测试报告中明确区分“已自动验证”和“已人工验证”。只跑 Vitest 或 Playwright 不能证明 Windows 原生能力完成，只跑 Rust 测试也不能证明用户主链路可用。

每次重要功能合并前，至少需要通过对应层级的测试：前端 UI 改动必须跑 Vitest 和相关 Playwright 用例；数据库或业务模型改动必须跑 Rust 单元/集成测试；平台适配改动必须补充 Windows 真实系统验收记录。若某项无法自动化，必须在 PR 或验收记录中写清楚人工验证步骤和结果。

## 7. 建议命令

前端单元测试建议使用：

```bash
npm run test
```

Playwright 端到端测试建议使用：

```bash
npm run test:e2e
```

Rust 默认测试建议使用：

```bash
cd src-tauri
cargo test
```

Windows 原生集成测试如果后续实现为显式开关，建议使用：

```bash
cd src-tauri
WINDOWS_NATIVE_TESTS=1 cargo test windows_native -- --ignored
```

具体命令以仓库根目录 `package.json`、`playwright.config.ts` 和 `src-tauri/Cargo.toml` 为准。
