# 工作区管理器产品需求文档

## 1. 产品定位

本产品是一个本地工作区管理器，用来帮助用户把完成某类工作所需的软件、窗口和记录内容组织在同一个工作区中。它本身不替代 VS Code、浏览器、终端、Obsidian、设计工具等专业软件，也不把这些软件强行嵌入到自己的界面内部，而是负责扫描软件、打开软件、记录当前工作区中已经打开的软件，并提供快速切换对应窗口的能力。

第一版优先面向 Windows 桌面环境开发，但产品结构需要为 macOS 迁移预留空间。跨平台迁移的核心原则是：产品层只表达“工作区、软件、窗口、白板、启动、切换”这些抽象能力，系统相关能力由平台适配层实现。Windows 版本可以先接入 Windows 的软件扫描、进程启动和窗口激活能力；未来 macOS 版本再替换为 macOS 的应用扫描、启动和窗口聚焦能力。

## 2. 目标用户与使用场景

目标用户是需要在不同任务之间频繁切换的人，例如开发者、设计师、运营人员、研究人员和内容创作者。这类用户通常不是只打开一个软件完成工作，而是围绕某个具体任务同时打开多个软件，比如代码编辑器、浏览器、文档、终端、数据库工具、截图工具和参考资料。

典型场景是：用户创建一个“AI 项目开发”工作区，然后从软件列表里点击 VS Code、Chrome、终端、Obsidian 等软件。产品负责启动这些软件，并把它们加入当前工作区左侧的软件栏。用户之后可以点击左侧图标切换到任意已经打开的软件窗口。与此同时，用户可以在右侧白板记录这个工作区的操作内容，例如当前任务、遇到的问题、关键截图、软件之间的操作步骤和后续待办。

## 3. 产品目标

第一版的核心目标是让用户能够用一个应用管理“某个工作区里打开过哪些软件，以及这些软件对应的工作记录”。产品不追求接管整个桌面，也不追求完整虚拟桌面能力，而是提供一个轻量、稳定、容易恢复上下文的工作入口。

第一版需要实现四件事：用户可以新建和切换工作区；用户可以从系统扫描出的软件列表中搜索并启动软件；当前工作区左侧可以展示已经通过本产品打开的软件；用户可以在白板中用卡片、截图和 Markdown 记录工作内容。

产品不应该在第一版承诺自动记录用户在每个软件内部做了什么，因为这会涉及隐私、权限、不同软件的兼容性和系统级监听问题。白板内容由用户主动记录，软件只负责提供记录空间和关联关系。

## 4. 核心概念

工作区是产品的最高层组织单位。一个工作区代表一类任务、一个项目或一个阶段性上下文，例如“论文写作”“求职准备”“后端开发”“剪辑项目”。每个工作区包含软件列表、窗口关联信息和白板内容。

软件是系统中可启动的应用程序。用户可以像按 Windows 键搜索软件名一样，在本产品中搜索软件并打开。产品需要从系统中扫描已安装软件，建立软件名称、图标、启动路径和平台类型之间的映射。

窗口是某个软件已经打开后的可切换对象。第一版中，一个软件可以先简化为对应一个主窗口；如果同一个软件打开了多个窗口，产品可以优先切换最近一次由当前工作区启动或绑定的窗口。后续版本再支持同一软件下的多窗口管理。

白板是工作区的记录区域。它不只是普通文本编辑器，而是类似 Obsidian Canvas 的可视化空间，支持用户拖动卡片、粘贴截图、编写 Markdown，并把记录内容与当前工作区上下文放在一起。

## 5. 用户流程

用户打开产品后，默认进入最近一次使用的工作区。如果没有工作区，则展示新建工作区入口。用户创建工作区时，只需要输入工作区名称，也可以后续补充描述、颜色或图标。

进入工作区后，界面左侧显示当前工作区已经打开或绑定的软件。中间区域可以展示当前工作区状态、软件搜索入口或白板入口，右侧或主区域提供白板操作空间。具体布局可以在设计阶段调整，但必须保证软件切换入口始终明显可见。

用户点击“添加软件”或直接在搜索框输入软件名称。产品从系统扫描的软件库中显示匹配结果。用户点击某个软件后，产品启动该软件，并把它加入当前工作区的软件列表。如果软件已经在当前工作区中存在，则直接切换到它的窗口，而不是重复添加。

用户点击左侧某个软件图标时，产品需要把系统焦点切换到该软件窗口。如果窗口已经关闭，产品应该提示“该软件窗口已关闭”，并提供重新打开入口。重新打开后，该软件仍归属于当前工作区。

用户在白板中可以创建 Markdown 卡片、粘贴截图、拖动卡片位置、缩放画布、整理记录。白板内容自动保存到当前工作区，不需要用户手动保存。

## 6. 功能需求

工作区管理需要支持创建、重命名、删除、切换和最近使用记录。删除工作区时，需要明确提示这会删除该工作区的软件关联和白板内容，但不会卸载任何系统软件，也不会关闭真实应用窗口。

软件扫描需要优先支持 Windows。第一版可以扫描开始菜单快捷方式、常见安装目录、注册表应用信息和用户手动添加的软件路径。扫描结果需要保存到本地软件库中，并支持手动刷新。用户还需要能手动添加任意 exe、快捷方式、文件夹、网址或命令，这样当系统扫描不完整时，仍然可以完成工作。

软件启动需要支持点击软件名称启动。启动后，产品要尽可能识别该软件对应的进程和窗口，并将其加入当前工作区。启动失败时，需要给出明确错误原因，例如路径不存在、权限不足、软件已卸载或启动命令无效。

窗口切换需要支持点击左侧软件图标后激活对应窗口。Windows 第一版需要处理窗口最小化、窗口被其他窗口遮挡、窗口已经关闭等情况。如果对应窗口最小化，需要恢复并置前；如果窗口不存在，需要提示重新打开。

左侧软件栏只展示当前工作区的软件，不展示全局所有正在运行的软件。软件栏中的每一项至少包含软件图标、软件名称、运行状态和关闭/移除入口。移除软件只表示从当前工作区解除关联，不等于关闭该软件或卸载该软件。

白板需要支持 Markdown 卡片、普通文本卡片、图片/截图卡片、拖拽移动、缩放、自动保存和基础撤销重做。截图可以通过粘贴剪贴板图片、拖入图片文件或调用系统截图能力加入白板。第一版不要求实现复杂多人协作、实时同步或高级绘图。

本地数据需要持久化保存。至少包括工作区信息、软件库、工作区软件关联、窗口绑定记录和白板内容。第一版可以使用本地数据库或结构化文件，但数据结构要便于后续迁移和备份。

## 7. 非功能需求

产品应该尽量轻量，不应该明显拖慢系统启动和软件打开速度。软件扫描可以在首次启动和用户手动刷新时执行，不应该频繁全盘扫描。窗口识别和状态刷新也不应该高频占用 CPU。

产品需要尊重用户隐私。第一版不自动读取软件内部内容，不监听键盘输入，不记录用户在外部软件里的具体操作。白板内容、软件列表和工作区配置默认只保存在本地。

产品需要具备跨平台迁移意识。产品内部不应该把 Windows API 调用散落在业务逻辑中，而应该把软件扫描、软件启动、窗口枚举、窗口激活、图标读取这些能力封装为平台接口。这样未来迁移到 macOS 时，主要替换平台适配层，而不是重写工作区和白板逻辑。

## 8. MVP 范围

第一版 MVP 应该优先完成工作区创建、Windows 软件扫描、软件搜索启动、当前工作区软件栏、窗口切换和基础白板。只要这条主链路稳定，产品就已经能表达核心价值。

MVP 可以暂不做自动操作日志、多窗口精细管理、跨设备同步、多人协作、插件系统、应用内嵌窗口、复杂权限管理和完整虚拟桌面能力。这些功能会显著提高复杂度，但不是验证产品价值的必要条件。

## 9. 界面结构建议

整体界面可以采用三栏结构。左侧是当前工作区的软件栏，展示已经加入该工作区的软件图标和状态。顶部或左上角提供工作区切换入口。主区域是白板，用户在这里记录当前工作区的内容。软件搜索入口可以放在左侧软件栏顶部，也可以通过快捷键呼出，交互上接近系统启动器。

软件搜索体验应该接近 Windows 开始菜单搜索。用户输入软件名后，结果即时过滤；点击结果后直接启动并加入当前工作区。对于已经加入当前工作区的软件，搜索结果可以显示“已在当前工作区”，点击后直接切换窗口。

白板交互应该接近 Obsidian Canvas 的核心体验，但不需要一开始复制全部能力。用户需要能自由放置记录卡片、图片和 Markdown 内容，通过拖动整理思路。白板不是说明页，而是用户真正工作的记录空间。

## 10. 后续版本方向

第二阶段可以增强窗口管理，例如支持同一软件多个窗口、窗口重命名、窗口截图预览、关闭窗口提醒和工作区恢复。也可以支持“重新打开工作区”能力，即用户进入某个工作区后，一键启动上次关联的软件。

第三阶段可以考虑 macOS 适配。迁移重点包括应用扫描、应用启动、窗口枚举、窗口激活、应用图标读取和系统权限申请。只要第一版把平台能力封装清楚，macOS 版本不需要重写工作区、白板和数据管理。

更长期可以考虑模板化工作区、白板内容导出、跨设备同步、自动化脚本和与常见工具的深度集成。但这些能力应建立在第一版主链路稳定之后，而不是在 MVP 阶段提前堆叠。

## 11. 验收标准

用户可以创建一个新工作区，在该工作区中搜索系统已安装的软件，并通过点击软件名称打开它。打开成功后，该软件会出现在当前工作区左侧软件栏中。用户点击左侧图标时，系统能够切换到对应软件窗口。

用户可以在白板中创建 Markdown 卡片，拖动卡片，粘贴截图，并在关闭产品后重新打开时看到上次保存的白板内容。不同工作区之间的软件列表和白板内容互不混淆。

当某个软件窗口已经关闭时，用户点击左侧图标不会产生无反馈状态，而是看到明确提示，并可以选择重新打开。删除工作区或移除软件关联不会误删、卸载或破坏用户系统中的真实软件。

第一版 Windows 功能完成后，代码结构中应该能明确区分产品业务层和 Windows 平台适配层。未来 macOS 迁移时，主要新增 macOS 平台适配实现，而不是大面积修改工作区、白板和数据存储逻辑。
